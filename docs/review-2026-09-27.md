# custom-news 实机核查报告（2026-09-27）

**结论先说**：**不需要大重构**。分层是站得住的（config → store → fetcher → renderer →
service → scheduler → matcher），问题集中在**少数重复实现**与**错误处理口径**上，
属于「定点清理」而非「推倒重来」。

本次核查方式是「只读代码审读 + 本地实测复现」：两份自动化审读覆盖 27 个模块 / 5235 行，
随后在真实部署（`render_width=3000`、16 个启用源、3 个推送时段）上复现失败路径。
所有数字都是本机实测，不是估算。

## 一、实测证据

| 项 | 实测值 | 说明 |
|---|---|---|
| 单张日报渲染 | **21.5s / 5.0MB / 峰值内存 4.35GB** | 3000px 宽 × dpr1.5 → 4500px 光栅、15 张卡片 |
| 深读图渲染 | 2.2s / 3.3MB | 840px 宽 |
| 同配置按默认 1280px | 约 0.9MB | 体积与宽度近似平方关系 |
| 非法 timezone 下定时任务数 | **6 → 0**（不可自愈） | `rebuild_jobs` 先全删再重建，`add_job` 抛异常即中断 |
| `GET /api/config` 回吐 | `password_sha`、`secret`、`llm_api_key` 明文 | 无任何脱敏 |
| WebUI 保存音乐设置 | 静默无效 | `ConfigUpdate` 缺 `music_chat` 字段，被 pydantic 丢弃 |
| `render.html.max_pixels` 注入 | **空转** | 已装 htmlrender 0.7.2 无该配置字段（整包 grep 无命中） |

内存这一项值得单独说：**4.35GB 峰值**解释了线上那次 46MB 日报图拖垮 NapCat 反向 WS 的事故——
渲染画布与 PIL 编解码的内存量跟着宽度平方增长，而当时的防护（`max_pixels`）是空转的。

## 二、已修复（3 个提交，53 个回归测试）

  音乐 cookie 置空。`secret` 是签发 Token 的 HMAC 密钥，**且改密码不会轮换它**，泄露不可撤销

- `ConfigUpdate` 补 `music_chat`
- 调度：时区前置校验 + 单时段独立兜底 + 非法配置保留现有任务（击杀开关已封）
- `timezone` / `weekdays` 输入校验；`misfire_grace_time` 1s → 300s
- 预生成文件名改用配置时区取日期（进程时区为 UTC 时原先永远命不中）
- 日报生成失败改为向推送目标发提示（原先注释声称「绝不能静默断更」，但兜底只覆盖深读分支）
- 上传背景图：体积检查提前到读入内存之前；PIL 预处理失败不再静默

## 四、CI 提案

前置准备（都在阶段 1/2 的范围内）：测试已就位（`tests/`）；建议再加 `ruff`；
bundle 由手工 `npm run build` + 复制改为 CI 校验「产物与源码同步」。

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv venv && uv pip install -e ".[dev]" nonebot2 nonebot-plugin-alconna nonebot-plugin-htmlrender
      - run: uv run python -m pytest
  bundle:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "20", cache: npm, cache-dependency-path: webui/package-lock.json }
      - run: npm ci --prefix webui && npm run build --prefix webui
      - name: 校验已提交的 bundle 与源码一致
        run: |
          rm -rf nonebot_plugin_custom_news/webui/dist
          cp -R webui/dist nonebot_plugin_custom_news/webui/dist
          git diff --exit-code -- nonebot_plugin_custom_news/webui/dist
```

## 六、渲染尺寸收敛（阶段 1 第 1 项，已实现）

**问题**：渲染宽度由 `render_width` 直通模板 CSS，再乘 dpr 得到光栅尺寸。
线上 `render_width=3000` × dpr1.5 = **4500px 光栅**，15 张卡片长图实测
**峰值内存 4.35GB / 21.5s / 5.0MB PNG** —— 这是 46MB 日报图拖垮 NapCat 反向 WS 的机理，
而当时的防护（`render.html.max_pixels`）在 htmlrender 0.7.2 上根本不存在。

**做法**：新增纯函数 `resolve_render_size(width, dpr)` 在渲染入口收敛，
**模板 CSS 宽度与光栅 dpr 同源**（只压 viewport 而页面本身还是宽的，截图仍是宽图——
第一版实现就踩了这个坑，已由 `2000×10858px` 的实测产出纠正）：

- CSS 宽度上限 `_MAX_RASTER_WIDTH = 2000`（聊天图显示宽度通常不到 1200px）
- dpr 压到不超过上限的倍数，但**不低于 1.0**（低于 1 是把文字降采样）
- 收敛时打 info 日志，不做静默降级

**实测（同一配置、同样 15 张卡片）**：

| | 收敛前 | 收敛后 |
|---|---|---|
| 光栅 | 4500px 宽（3000×1.5） | 2000px 宽（2000×1.0） |
| 峰值内存 | 4.35GB | **1.69GB（-61%）** |
| 耗时 | 21.5s | **6.5s（-70%）** |
| 产物体积 | 5.0MB | **2.4MB（-52%）** |

默认 `render_width=1280` 的行为完全不变（1280×1.5=1920 本就在上限内），
因此对既有用户无感知变化；部署侧已把线上 `render_width` 从 3000 调整为 2000。
新增 5 个单测钉住边界：默认值不被改动、dpr 不低于 1.0、荒谬输入、像素数单调递减。
